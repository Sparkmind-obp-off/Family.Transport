SESSION 5-E — API CONTRACT

5-E.1 — API PRINCIPLE

Architecture:

CLIENT
  ↓
API
  ↓
AUTH / RBAC
  ↓
VALIDATION
  ↓
DOMAIN LOGIC
  ↓
DATABASE
  ↓
EVENT / NOTIFICATION

Rule utama:

> Frontend hanya meminta. Backend yang memutuskan.



Jadi:

frontend tidak menentukan harga final

frontend tidak menentukan availability

frontend tidak menentukan permission

frontend tidak menentukan booking status

frontend tidak menentukan payment status

5-E.6 — AVAILABILITY API

🔥 Core endpoint.

POST

/api/v1/availability/check

Request:

{
  "service_id": "svc_123",
  "start_at": "2026-08-20T09:00:00",
  "end_at": "2026-08-20T17:00:00",
  "passengers": 4,
  "vehicle_category_id": "cat_01"
}

Server performs:

service validation
      ↓
date validation
      ↓
capacity filtering
      ↓
service compatibility
      ↓
booking conflict
      ↓
maintenance conflict
      ↓
driver/resource conflict

Response:

{
  "success": true,
  "data": {
    "available": true,
    "vehicles": []
  }
}


---

5-E.7 — AVAILABILITY RULE

Vehicle dianggap eligible jika:

ACTIVE
AND capacity >= passengers
AND service compatible
AND no overlapping confirmed booking
AND no maintenance block
AND operational constraints satisfied


---

5-E.8 — OVERLAP RULE

Dua trip conflict jika:

existing.start < requested.end
AND
existing.end > requested.start

Ini menjadi canonical overlap rule.

Jangan membuat versi berbeda di frontend/backend.

5-E.12 — BOOKING TRANSITIONS

DRAFT
 ↓
PENDING
 ↓
QUOTED
 ↓
CONFIRMED
 ↓
COMPLETED

5-E.35 — TRANSACTION BOUNDARY

Booking confirmation harus atomic.

Conceptually:

BEGIN TRANSACTION

revalidate resource
create/update booking
reserve vehicle
create trip if applicable
create event

COMMIT

Jika salah satu critical operation gagal:

> rollback.




---

5-E.36 — CONCURRENCY PROTECTION

Scenario:

Customer A → Vehicle X
Customer B → Vehicle X

secara bersamaan.

System harus memastikan:

A → SUCCESS
B → CONFLICT

atau sebaliknya.

Tidak boleh:

A → SUCCESS
B → SUCCESS

untuk resource yang sama dan waktu overlapping.
