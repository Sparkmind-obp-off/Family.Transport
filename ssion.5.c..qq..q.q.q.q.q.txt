SESSION 5-C — USER STORIES + ACCEPTANCE CRITERIA

Sekarang kita turunkan Feature Inventory 5-B menjadi perilaku user yang bisa dites.

Prinsip:

> User Story menjelaskan kebutuhan. Acceptance Criteria menentukan kapan kebutuhan itu dianggap benar-benar selesai.




---

5-C.1 — FORMAT STANDARD

Setiap story:

ID
Actor
Goal
User Story
Business Context
Acceptance Criteria
Dependencies
Priority

Acceptance Criteria kita tulis dengan:

GIVEN
WHEN
THEN


---

5-C.2 — CUSTOMER DISCOVERY

US-CUS-001 — View Homepage

Story

> Sebagai customer, saya ingin memahami layanan Family Transport dengan cepat, sehingga saya tahu apakah layanan ini cocok untuk kebutuhan perjalanan saya.



Acceptance Criteria

GIVEN customer membuka homepage
WHEN halaman selesai dimuat
THEN customer dapat melihat:
- layanan utama
- fleet/service options
- service area
- alasan memilih Family Transport
- primary CTA booking

Dan:

WHEN customer menekan "Book Transport"
THEN customer diarahkan ke booking flow.


---

5-C.3 — SERVICE DISCOVERY

US-CUS-002 — View Services

> Sebagai customer, saya ingin melihat jenis layanan transport yang tersedia, sehingga saya dapat memilih layanan yang sesuai.



GIVEN services aktif tersedia
WHEN customer membuka service catalog
THEN hanya service aktif yang ditampilkan.

WHEN customer memilih service
THEN system membuka service detail.

THEN customer tidak dapat membuat booking baru

5-C.5 — VEHICLE DISCOVERY

US-CUS-004 — Vehicle Catalog

> Sebagai customer, saya ingin melihat kendaraan yang tersedia, sehingga saya bisa memilih kendaraan yang sesuai kebutuhan.

5-C.7 — START BOOKING

US-CUS-006 — Start Booking

> Sebagai customer, saya ingin memulai booking dari website, sehingga saya dapat meminta transport tanpa harus menghubungi operator terlebih dahulu.

THEN booking wizard terbuka

5-C.8 — SELECT SERVICE

US-CUS-007

> Sebagai customer, saya ingin memilih jenis layanan yang saya perlukan.



GIVEN customer berada pada Step 1
WHEN customer memilih service
THEN service tersimpan pada booking draft.

Jika service inactive:

THEN service tidak dapat dipilih.


---

5-C.9 — SELECT DATE & TIME

US-CUS-008

> Sebagai customer, saya ingin menentukan waktu perjalanan.



GIVEN customer berada pada Step 2
WHEN customer memasukkan start dan end
THEN system memvalidasi waktu.

Jika:

end <= start

maka:

> ❌ invalid request.

5-C.10 — LOCATION

US-CUS-009

> Sebagai customer, saya ingin memasukkan pickup dan destination.



GIVEN customer berada pada Step 3

THEN data tersimpan ke booking draft.

MVP:

5-C.11 — PASSENGERS

US-CUS-010

> Sebagai customer, saya ingin menentukan jumlah penumpang sehingga system dapat mencarikan kendaraan yang cukup.



GIVEN passengers = 7
WHEN availability dijalankan
THEN vehicle dengan capacity < 7 tidak boleh muncul.

🔥 Ini business rule, bukan sekadar UI filter.

5-C.12 — AVAILABILITY

US-CUS-011 — Check Availability

> Sebagai customer, saya ingin mengetahui kendaraan yang tersedia pada waktu perjalanan saya.



GIVEN request valid
WHEN customer melakukan availability check
THEN system mencari kendaraan eligible.

System harus mengecek:

active
service compatibility
capacity
booking conflicts
maintenance
driver availability jika diperlukan

5-C.13 — NO AVAILABILITY

US-CUS-012

WHEN availability check selesai
THEN system menampilkan:
"No vehicle available for this request."

> menampilkan kendaraan unavailable seolah tersedia.

5-C.23 — STALE AVAILABILITY

US-CUS-022

Scenario:

Customer melihat:
Vehicle A available

Kemudian customer menunggu.

Customer klik:

> Confirm.



Ternyata Vehicle A sudah dibooking orang lain.

Expected:

THEN system rejects confirmation
AND informs customer
AND offers available alternatives.

🔥 Ini wajib dites.


---

5-C.24 — BOOKING CONFIRMATION

US-CUS-023

GIVEN quote accepted
AND resource available
WHEN transaction succeeds
THEN booking dibuat
AND booking_code dihasilkan
AND customer mendapat confirmation.


---

5-C.25 — IDEMPOTENT BOOKING

US-CUS-024

Scenario:

Customer menekan tombol:

> Confirm



dua kali.

Expected:

GIVEN same idempotency key
WHEN request dikirim ulang
THEN system tidak membuat duplicate booking.

🔥 Critical acceptance test.

5-C.46 — COMPLETE END-TO-END STORY

Ini Golden User Story.

US-E2E-001

> Sebagai customer, saya ingin memesan transport sampai perjalanan selesai.



Flow:

Visit website
 ↓
Choose service
 ↓
Choose date
 ↓
Enter location
 ↓
Enter passengers
 ↓
Check availability
 ↓
Select vehicle
 ↓
Add add-ons
 ↓
Enter contact
 ↓
Review
 ↓
Get quote
 ↓
Accept
 ↓
Booking confirmed
 ↓
Payment
 ↓
Driver assigned
 ↓
Trip
 ↓
Completed

Acceptance:

GIVEN valid customer request
WHEN customer completes booking flow
THEN confirmed booking exists
AND vehicle is reserved
AND payment state is tracked
AND trip can be operated
AND final trip can be marked COMPLETED.

🔥 Kalau E2E ini berhasil, MVP CORE HIDUP.

5-C.47 — CRITICAL EDGE CASE MATRIX

Kita wajib test minimal:

Scenario	Expected

Invalid date	Reject
End before start	Reject
Passenger > capacity	Reject
Vehicle inactive	Reject
Vehicle already booked	Reject
Maintenance conflict	Reject
Driver conflict	Reject
Quote expired	Reject
Price tampered	Reject
Unauthorized admin API	403
Duplicate booking request	No duplicate
Payment webhook duplicate	No duplicate
Payment webhook invalid	Reject
Vehicle deactivated	Existing history preserved
