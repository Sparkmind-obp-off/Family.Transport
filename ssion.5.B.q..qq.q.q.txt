5-B.18 — CONTOH F-016

F-016 — Availability Check

Purpose

Menentukan kendaraan yang benar-benar tersedia untuk request.

Actor

Customer / Operator.

Input

service_id
start_at
end_at
passengers
vehicle_category?

Business Rules

vehicle.active = true
service compatible
capacity >= passengers
no booking overlap
no maintenance overlap
driver available if required

Output

eligible vehicles[]
availability status

Errors

INVALID_DATE
NO_VEHICLE_AVAILABLE
SERVICE_UNAVAILABLE


---

5-B.19 — ACCEPTANCE CRITERIA F-016

Feature dianggap selesai jika:

✓ unavailable vehicle tidak muncul
✓ capacity mismatch tidak muncul
✓ maintenance conflict ditolak
✓ booking overlap ditolak
✓ driver conflict ditolak
✓ valid vehicle muncul
✓ result berasal dari server
✓ simultaneous request tidak menyebabkan double booking

🔥 Ini baru testable feature.

🚀 NEXT — SESSION 5-C

Sekarang kita masuk bagian yang lebih granular:

USER STORIES + ACCEPTANCE CRITERIA

Kita akan menulis dari perspektif nyata:

> “Sebagai customer, saya ingin…, sehingga…”



Contoh:

US-CUS-001

Sebagai customer,
saya ingin memilih tanggal dan waktu perjalanan,
sehingga saya bisa mengetahui kendaraan
yang tersedia pada waktu tersebut.

Lalu kita turunkan menjadi:

Given
When
Then

Jadi nanti bukan cuma:

> “buat booking.”



Tetapi benar-benar:

> apa yang user lakukan + apa yang system wajib lakukan + bagaimana developer tahu bahwa feature tersebut benar.
