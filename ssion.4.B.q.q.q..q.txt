4-B.14 — BOOKING SNAPSHOT

Saat customer melakukan booking, data penting jangan hanya mengandalkan master records.

Misalnya:

Hari ini:

> Toyota Innova = Rp500k



Bulan depan:

> Toyota Innova = Rp600k



Booking lama harus tetap:

> Rp500k.



Karena itu kita simpan:

price_snapshot
vehicle_snapshot
service_snapshot

atau struktur snapshot JSON yang tervalidasi.

🔥 Historical truth > current master data.

4-B.20 — AVAILABILITY

Kita tidak perlu menyimpan available = true/false sebagai source of truth.

Availability adalah derived state.

System menghitung dari:

vehicle active
+
service compatible
+
booking conflict = false
+
maintenance conflict = false

Jadi:

Availability = COMPUTED

bukan data manual yang gampang stale.

4-B.33 — DATABASE DESIGN PRINCIPLE

Ada 4 prinsip yang kita lock.

1. NORMALIZED MASTER DATA

Vehicle, customer, service, driver tidak diduplikasi sembarangan.

2. SNAPSHOT TRANSACTION DATA

Harga / informasi penting saat transaksi disimpan sebagai snapshot.

3. DERIVED STATE

Availability dihitung dari sumber data.

4. AUDITABLE HISTORY

Perubahan penting tidak menghilangkan historical truth.

4-B.34 — SOFT DELETE

Untuk business records penting:

Jangan buru-buru:

DELETE FROM vehicles

Lebih aman:

active = false

atau:

deleted_at

Karena booking lama masih membutuhkan reference vehicle tersebut.

4-B.35 — TIMESTAMP STANDARD

Semua timestamp database:

UTC

> timezone lokal bisnis/customer.



Ini menghindari masalah timezone ketika trip melibatkan user dari wilayah berbeda.

4-B.36 — ID STRATEGY

Gunakan internal ID yang aman untuk database.

Misalnya:

> UUID / UUID-like identifier.



Customer-facing code terpisah:

internal id:
xxxxxxxx-xxxx-...

booking_code:
FT-2026-000123

Jangan expose sequential database ID sebagai public identifier utama.

4-B.39 — DOUBLE BOOKING PROTECTION

Ini salah satu bagian paling kritis.

Tidak cukup:

Frontend check

Tidak cukup:

API check

Database / transaction layer juga harus melindungi.

Flow:

REQUEST
 ↓
BEGIN TRANSACTION
 ↓
CHECK CONFLICT
 ↓
LOCK / CONSTRAINT
 ↓
CREATE BOOKING
 ↓
COMMIT

🔥 Karena dua customer bisa submit hampir bersamaan.
